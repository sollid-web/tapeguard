---

1. Executive Summary

TapeGuard is an autonomous crypto-trading agent designed for X Layer.

Its architecture combines:

- Solidity smart contracts ("AgentContainer.sol", "PolicyCircuit.sol").
- A Cloudflare Worker execution daemon.
- Cloudflare D1 database storage.
- Oracle and market-price integrations.
- A browser-based frontend.
- Automated transaction execution and policy enforcement.

The project has a functional architectural foundation, but the review identified several areas where execution reliability, accounting correctness, oracle safety, RPC validation, and operational security require improvement.

The most important finding: some protections already exist in the source code, but the system still has weaknesses in transaction sequencing, trade accounting, tick-lock ownership, RPC validation, and oracle fail-safe behaviour.

The review distinguishes existing protections from unresolved vulnerabilities. It does not treat an existing protection as a new fix.

3. Findings and Technical Assessment

A. Smart Contract Security

C1 — ERC-20 allowance and router exposure

Status: Partially mitigated; residual risk remains.

The contracts already include token-specific spending rules and checks for direct ERC-20 methods, including approval-related methods.

However, router calldata is not semantically decoded by the container. This means the container cannot fully determine what a router call will do with an approved token.

A router may subsequently call "transferFrom" using an allowance granted earlier.

Risk:

- Token allowances may remain available beyond the intended execution.
- Router interactions may create exposure that is not fully represented by direct token-call checks.
- A compromised or malicious execution path could potentially exploit previously granted allowances.

Required improvements:

- Review every approval path.
- Prefer exact allowances over unlimited approvals.
- Reset allowances after successful execution where appropriate.
- Define failure handling for swaps and approval resets.
- Add tests for malicious router calldata and unexpected token pulls.
- Do not claim complete protection until the router allowance lifecycle is demonstrably controlled.

C2 — Agent activation expiry

Status: Existing protection confirmed.

"AgentContainer.execute()" checks activation through "isActive()".

This means execution is subject to the agent's activation period.

No additional fix should be claimed without identifying a separate expiry bypass.

C3 — Accrued service fees and available balance

Status: Existing protection confirmed.

Native execution uses an available-balance calculation that excludes accrued service fees.

This prevents the execution path from treating accrued fees as freely spendable agent funds.

C4 — Missing on-chain daily action limit

Status: Implemented in source; pending deployment and verification.

PolicyCircuit now tracks a UTC-day action counter per agent and enforces owner-configured maxActionsPerDay during recordExecution. Contract redeployment and integration tests are still required.

Risk:
If the off-chain execution layer is compromised or bypassed, the smart contract does not independently enforce the same daily action restriction.

Required improvements:

- Add an on-chain daily action counter.
- Enforce the maximum inside the policy validation path.
- Record successful executions on-chain.
- Include the limit in the policy commitment.
- Add an owner-controlled configuration mechanism.
- Test day-boundary behaviour and repeated execution attempts.

Deployment implication: Solidity changes require contract redeployment and corresponding updates to the container and policy wiring.

C5 — Empty calldata and plain native transfers

Status: Existing protection confirmed.

The contract requires explicit permission for empty-calldata execution and plain transfers.

This reduces the risk of unintended native-asset transfers through generic execution paths.

C6 — Spend recording without successful execution

Status: Existing protection confirmed.

Spend recording is nonce-bound and occurs within the execution path.

This provides protection against recording spend independently of the associated execution.

C7 — Owner withdrawal behaviour

Status: Design decision, not automatically a vulnerability.

Owner withdrawal is intentionally available as a recovery mechanism.

The owner is a trusted authority in this design.

The documentation should clearly explain that owner withdrawal is an administrative trust assumption rather than describing the contract as trustless.

B. Backend and Worker Reliability

S1 — Unauthenticated execution ticks

Status: Existing protection confirmed.

"/api/tick" requires an owner session or daemon secret.

The endpoint is not simply an unrestricted public execution trigger.

S2 — Oracle fail-safe behaviour

Status: Implemented in source; feed-failure tests and deployment verification pending.

The oracle now rejects execution when the required secondary feed is unavailable and never uses cache entries older than 60 seconds. The oracle already includes:

- Manual price input.
- CoinGecko integration.
- OKX integration.
- Price caching.
- Deviation checks.
- An on-chain DEX quote.

However, the reviewed implementation does not consistently fail closed when an independent secondary feed is unavailable. A stale cached value may also be returned.

There is no sufficiently comprehensive TWAP, liquidity, or price-impact protection.

Risk:
A stale or manipulated price may influence an automated trading decision.

Required improvements:

- Separate display prices from executable trading prices.
- Reject stale prices for execution.
- Require the configured independent price sources to be available.
- Reject excessive deviation.
- Add liquidity and price-impact constraints.
- Consider TWAP or other manipulation-resistant pricing.
- Test missing feeds, stale cache, extreme deviation, and manipulated market conditions.

A price suitable for displaying information should not automatically be considered safe for authorizing a trade.

S3 — Hot keeper key

Status: Residual operational risk.

The Worker relies on a keeper signing key stored as a secret.

This is a common operational pattern, but it creates a concentrated security risk.

Required improvements:

- Use a dedicated, minimally funded execution wallet.
- Restrict permissions and spending exposure.
- Establish key rotation and emergency revocation procedures.
- Monitor abnormal transaction activity.
- Avoid exposing signing material to frontend code or logs.
- Consider stronger signing infrastructure where practical.

A compromised keeper key remains a serious operational threat even when the smart contracts enforce policy restrictions.

S4 — Transaction nonce collisions

Status: Implemented in source; pending runtime verification.

The engine now initializes a per-tick nonce context and increments it for each submitted transaction step, including multi-step plans.

Rapid transaction submission can result in multiple steps attempting to use the same nonce.

Risk:

- Rejected transactions.
- Replaced or stuck transactions.
- Broken approval/swap/reset sequences.
- Inconsistent queue state.

Required improvements:

- Maintain a per-tick nonce sequence.
- Reserve and increment the nonce for each submitted transaction.
- Handle retries and replacements explicitly.
- Test multiple transaction steps in a single execution cycle.

D1 — Daily trade accounting

Status: Implemented in source; D1 migration and lifecycle tests pending.

Queue rows now carry a shared logical trade_id for multi-step plans, and tradesLastDay() counts distinct logical trades rather than transaction-step rows.

The transaction queue represents individual transaction steps, not necessarily complete logical trades.

Additionally, pending transactions that become confirmed can disappear from the count when their status changes.

Risk:

- One logical trade with multiple transaction steps can be counted multiple times.
- Confirmed trades can be omitted from the daily count.
- The configured daily limit may not represent actual completed trading activity.

Required improvements:

- Introduce a logical trade identifier.
- Associate approval, swap, and reset transactions with the same trade.
- Track logical trade lifecycle independently of individual transaction steps.
- Count completed or appropriately classified logical trades.
- Add a D1 migration and tests for pending, confirmed, failed, and retried transactions.

D2 — Tick-lock ownership

Status: Implemented in source; concurrency and lease-renewal tests pending.

The tick lock now stores a unique lease token and release uses an atomic token match, preventing delayed ticks from clearing a newer lock.

Risk:
A delayed execution could release a lock acquired by a newer execution cycle.

This can permit overlapping ticks.

Required improvements:

- Assign a unique owner token to each lock acquisition.
- Use a lease with an appropriate expiry.
- Renew the lease during long-running execution.
- Release the lock only if the owner token still matches.
- Test delayed ticks and overlapping execution attempts.

D3 — RPC request validation

Status: Implemented in source; abuse-boundary tests pending.

/api/rpc now enforces body and batch limits, strict block-tag/range validation, blockHash constraints, upstream timeout, and response-size limits.

The reviewed "eth_getLogs" block-range validation can be bypassed in certain cases involving nonnumeric block tags because the numeric range check is not consistently applied.

Required improvements:

- Enforce a maximum request-body size.
- Limit JSON-RPC batch size.
- Validate supported block tags.
- Validate "fromBlock" and "toBlock".
- Enforce a maximum log-query range.
- Validate "blockHash" requests.
- Apply upstream timeouts.
- Limit upstream response sizes.
- Reject malformed requests consistently.

RPC proxy endpoints must be treated as resource-control boundaries, not transparent unrestricted relays.

C. Frontend Security and Maintainability

P1 — Browser session storage

Status: Existing improvement confirmed.

The reviewed frontend uses "sessionStorage" with an eight-hour expiry rather than relying on a persistent "localStorage" session.

This reduces the persistence of browser session data.

It does not eliminate risks from malicious scripts running in the page.

Further consideration:

- Review XSS exposure.
- Avoid placing sensitive signing material in browser storage.
- Keep authentication and authorization checks on the server.
- Apply a suitable Content Security Policy.

D7 — Monolithic frontend

Status: Maintainability issue.

The main "index.html" file is approximately 183 KB.

This creates difficulties for:

- Code review.
- Isolated testing.
- Debugging.
- Reuse.
- Long-term maintenance.
- Safe feature development.

Required improvements:
Refactor into logical modules, such as:

- Application initialization.
- Wallet connection.
- Agent configuration.
- Trading dashboard.
- Policy management.
- Transaction history.
- API client.
- UI components.

This is not an immediate exploit by itself. It is a maintainability and regression-risk issue.

The refactor should be performed with behaviour-preservation tests rather than a blind rewrite.

D. Testing, Build and Delivery

D4 — Missing automated test infrastructure

Status: Open.

The reviewed repository did not contain a complete automated testing and reproducible-build setup.

The review found no established comprehensive combination of:

- Foundry configuration and contract tests.
- Node test suite for Worker logic.
- CI pipeline.
- Reproducible deployment checks.

Required improvements:

- Add Foundry configuration.
- Test smart-contract policy enforcement.
- Add Node tests for backend execution and RPC validation.
- Test oracle failure conditions.
- Test transaction sequencing and accounting.
- Add CI workflows.
- Document local test and deployment commands.

A project that controls automated financial execution needs repeatable tests for both normal operation and failure conditions.

5. Recommended Remediation Order

The following order prioritizes financial safety and execution correctness.

Phase 1 — Execution and transaction safety

1. Fix tick-lock ownership and lease renewal.
2. Implement deterministic per-tick nonce sequencing.
3. Correct logical-trade accounting.
4. Harden RPC request validation.
5. Add tests for transaction queue failure and retry behaviour.

Phase 2 — Oracle and contract policy enforcement

1. Make executable pricing fail closed on stale or unavailable required feeds.
2. Add liquidity and price-impact constraints.
3. Introduce an on-chain daily action limit.
4. Review allowance lifecycle and router interactions.
5. Add smart-contract tests for policy bypass attempts.

Phase 3 — Testing and operational security

1. Add Foundry tests.
2. Add Node backend tests.
3. Establish CI.

9. Final Engineering Assessment

TapeGuard has a meaningful architecture for an autonomous trading system, but the review identified important gaps between individual security checks and end-to-end execution safety.

The highest-priority concerns are:

1. Transaction integrity: nonce sequencing, tick-lock ownership, and logical-trade accounting.
2. Execution authorization: oracle freshness, independent feed availability, and price-impact safeguards.
3. On-chain enforcement: daily action limits and allowance lifecycle controls.
4. Operational security: keeper-key exposure and emergency response.
5. Engineering assurance: automated testing, CI, and accurate security documentation.

The most important architectural principle going forward is that security controls should be enforced at the layer where they can be independently verified.

Off-chain checks should not be the only protection for critical financial limits. Likewise, a successful transaction submission should not be treated as proof that a logical trade completed correctly.

Audit conclusion: TapeGuard requires further remediation and verification before its security posture can reasonably be described as production-ready for autonomous financial execution.

14. Frontend Modularization Status

The frontend runtime was externalized from the monolithic `index.html` into `modules/app.js` while preserving the static deployment entry point, injected `window.APP_CONFIG`, contract ABIs, API paths, wallet behavior, DOM identifiers, and CSS. `index.html` now loads the runtime with:

`<script type="module" src="./modules/app.js"></script>`

The first incremental module boundaries are now implemented:

- `modules/core.js`: shared DOM, formatting, parsing, random-value, and byte helpers.
- `modules/codec.js`: Keccak, ABI encoding/decoding, input parsing, selector self-test, and ABI word encoding.
- `modules/config.js`: validated deployment configuration, chain settings, contract metadata, and configuration warnings.
- `modules/state.js`: state constants, storage adapters, and pure default-state construction.
- `modules/app.js`: composition root and remaining runtime behavior.

All frontend modules pass Node syntax checks. The state loading lifecycle and tightly coupled policy, wallet, RPC, daemon, and rendering functions remain in `app.js pending explicit context/factory extraction. No frontend browser smoke test or live X Layer deployment verification has been performed. This status records source-level modularization only and must not be treated as proof of deployment or production readiness.

14. Recheck Remediation — Verified Source Changes

The highest-priority ERC-20 parser fix is now applied in both the application and deployment copies of `AgentContainer.sol`: sensitive selectors reject noncanonical calldata, including appended trailing bytes, before token accounting and router checks. Deployment Foundry tests now include canonical token-policy enforcement and padded approval rejection using a mock ERC-20; the full suite passes 13 tests.

`PolicyCircuit._bumpCommitment()` now includes `maxActionsPerDay` in the same ABI-encoded order as `computeCommitment()`. A regression test verifies equality after construction and policy mutations. Worker queue inserts for rejected and successfully sent actions now persist `trade_id`, failed swap cleanup carries the originating trade ID, and queue API responses expose the logical trade ID. `/api/rpc` now rejects unbounded or symbolic `eth_getLogs` ranges and uses bigint-safe canonical hex range checks. Node regression tests pass 14/14 and Foundry tests pass 13/13 locally.

The queue now assigns explicit `stepIndex`/`dependsOn` metadata, stops submitting dependent steps after a predecessor is queued or rejected, gates queue draining on the predecessor's sent/confirmed status, and keeps failed-swap cleanup in the same queued workflow. Nonce contexts now advance only after a successful broadcast, and queue draining renews the tick lease before each row; expired leases cannot be renewed. Node syntax and all 14 backend tests pass after these changes.

The market-risk phase now validates only configured USDT↔wrapped-native two-token pools, identifies reserve sides by token address rather than path position, preserves asymmetric decimals, and computes price impact from the reserve marginal/no-trade output versus the router quote. Oracle deviation remains a separate check. Node syntax and all 14 backend tests pass after this change.

Queue rows now use an additive `claim_token` migration and an atomic pending→processing update before drain submission. Status updates require the matching claim token, and stale processing rows are expired rather than being silently retried by competing ticks. Node syntax and all 14 backend tests pass after this change.

Submission now treats a send timeout as ambiguous: it checks the relayer's pending nonce before deciding whether to retry, records an `unknown-nonce:<n>` sent marker when the nonce advanced, and avoids rebroadcasting at a new nonce. Tick execution now runs a periodic lease heartbeat and aborts further submissions when renewal is lost. Node syntax and all 14 backend tests pass after this change.

The Foundry deployment workspace now has an explicit `foundry.toml` pinned to Solidity 0.8.24 with optimizer/fuzz settings and an X Layer testnet endpoint, plus a GitHub Actions workflow that runs formatting, build, and tests. The application repository now has a Node GitHub Actions workflow running `npm test`. `forge build` succeeds locally with existing lint warnings.

`PolicyCircuit.check()` now enforces the same UTC-day action counter used by `recordExecution()`, so `AgentContainer.simulate()` no longer approves an action that execution will reject with `ActionsAboveLimit`. A Foundry regression covers the exhausted-action-budget verdict. The deployment Foundry suite passes 14 tests.

The Foundry contracts and tests are now formatter-clean: `forge fmt --check` passes. The complete deployment workspace suite passes 14 tests after formatting, including action-limit simulation parity and ERC-20 trailing-calldata regressions.

These source-level fixes are not deployed. Receipt reconciliation for unknown nonce markers, multi-hop reserve/impact validation, full D1 migration verification, CI execution on the remote repositories, and X Layer Testnet deployment remain open and must be completed before claiming the audit resolved.

The tested Foundry workspace has now been copied into `/root/tapeguard/foundry` so the project contains the contracts, tests, deployment script, pinned dependency metadata, and CI evidence used for verification. Secrets, cache, and generated build output are excluded. The copied canonical workspace passes `forge fmt --check`, `forge build`, and the complete 14-test suite. The configured X Layer testnet RPC was checked read-only and returned chain ID 1952 (`0x7a0`). Compiled AgentContainer and PolicyCircuit ABI arrays were exported under `/abi` and embedded into `index.html`; the frontend configuration now targets chain ID 1952. Redeployment was not executed because the environment denied the production-deploy command, so no new addresses or deployment receipts are claimed.
